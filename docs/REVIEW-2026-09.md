# Whole-app review — 18 Sep 2026

Owner's brief: "Is it optimized or can we do better? Do not add things for
the sake of it. A genuine plan. Nothing may break."

Method: measured (bundle, production TTFB, DB round-trips per screen,
dependency advisories), then the five review roles ran blind and in
parallel — device-tester (every screen at phone width), data-steward
(schema, pipeline, backups, write paths), editor (every string), adversary
(live handoff, ramp, gym scoping, clocks), trainer (the program against
his medical context). Findings below are only what was observed or proved.

## Verdict

**Speed is not the problem.** Client bundle 87 kB shared / 120 kB worst
screen; production TTFB 200–260 ms per screen; 7–25 DB round-trips per
screen but parallel. The only perf fact worth knowing is a 1–2 s
cold-start tail (serverless + Neon waking) — infrastructure, not code.

**Correctness and consistency are the problem.** Three clocks (Riyadh
calendar day, 04:00 activity day, server UTC) disagree on screens he
opens back to back; the program's arithmetic meets his real loads and
lies (the ramp counted an override as compliance); two prescriptions are
medically wrong for a flecainide/AF/hypertension patient; and the data
layer has three ways to silently corrupt rows that happen not to have
fired yet.

Hygiene is genuinely good: zero TODOs, 3,713 assertions, daily snapshot
unbroken since 19 Aug, build-script rule mechanically tested, no
horizontal overflow at 320 px, the three historical iOS layout bugs have
not regressed.

**Correction to what the cloud session told him on 18 Sep:** production
had him at REBUILD **70%**, not RELOAD 85% — the 85% came from test rows
that exist only in the local restore. Thursday's lifts were 96–117% of
his pre-break base. The recommendation (advance to RESTORE now) stands.

## Rules for every item below

1. One item, one commit, own revert. Vercel redeploys the previous build
   in ~1 min; `git revert` is the rollback for everything in Tier 1–3.
2. `npm test` + `npm run lint` + production build with an unreachable
   DATABASE_URL before every push. Assertions are added against his
   REAL history for every logic change.
3. Schema changes only through Apply-schema — and only after Tier 0
   fixes its gate. Every schema change here is additive (a unique index,
   a dropped default).
4. Live-DB repairs only through run-history-script, preview then apply.
5. A restore is REHEARSED (Tier 0) before anything in Tier 2 touches the
   schema.
6. The relevant review role re-reads each tier's diff blind before merge.
7. Nothing in `ios/` or `native/` is touched from the cloud session; Watch
   items are written up for the Mac session and, where the server can
   carry the fix instead, the server carries it.

## Not doing, and why

- No framework majors (above). No Prisma 7, no Tailwind 4.
- Not splitting `WorkoutForm.tsx` (2,349 lines). The risk is real, the
  user value is zero; logic keeps leaving it into tested pure libs
  (`live-session.ts`, `program.ts`) when it needs to, which is the right
  pattern.
- No performance work. The numbers do not justify it.
- No connection-pool tuning or new indexes — irrelevant below ~10k sets.
- No new features. Siri and the crown stay queued as Mac build 10 exactly
  as the owner asked; nothing is added beyond that.

## Order

breaks" true rather than hoped. Then 1.1–1.4 (medical) the same day. Then
the rest of Tier 1 and Tier 2 in small commits with the trainer /
steward / adversary re-reading each. Tier 3 last; 3.1 can go early since
it is one component and Mac-checkable.
